## 致命坑：better-sqlite3 在阿里云 CentOS8/Alinux2 (glibc 2.28) 无法运行（已根治）
- 现象：进程反复 `errored`，日志 `Error: /lib64/libm.so.6: version GLIBC_2.29 not found (required by .../better-sqlite3/prebuilds/linux-x64.node)`。
- 根因：better-sqlite3@13 的 npm 预编译包绑定 glibc 2.29，本机只有 2.28，require 即崩。不能手动升级 glibc。
- 走过的弯路（均失败）：`npm rebuild --build-from-source`（被 prebuild-install 短路，没编译）；`npm install --build-from-source`（同样被短路）；手动 `npx node-gyp rebuild` 删 prebuilds 后 `MODULE_NOT_FOUND`（node-gyp 也没真正产出 build/Release）。
- **最终根治**：把数据库从 better-sqlite3 换成 **sql.js（SQLite 纯 WASM，零原生编译）**。
  - `db.js` 接口保持 `loadState/saveState/migrateIfNeeded` 不变，新增 `init()`（异步，返回 promise，server.js 启动时 `await db.init()` 后再 `loadState`）。
  - sql.js API 注意点（与 better-sqlite3 不同）：①`stmt.get()` 返回**按列位置的数组**，需 `stmt.getColumnNames()` 映射成对象；②写操作必须先 `stmt.bind(params)` 再 `stmt.run()`（`stmt.run(params)` 不会绑定）；③`initSqlJs({wasmBinary})` 用同步读好的 wasm 传进去，避免运行时再异步读文件。
  - **不要用 deasync** 在 require 阶段阻塞等 WASM 初始化：deasync 用 `process.nextTick` 让出事件循环，会饿死 macrotask（异步文件 I/O / `onRuntimeInitialized` 的 setTimeout），导致死锁卡死。
- 已提交 `0030402`，但 `git push` 在本环境被代理阻断（SIGTERM），需用户本地 `git push`。
- 服务器现有 `data/pingfen.db` 是 better-sqlite3 的 WAL 库；切换后若 WAL 未 checkpoint，主文件可能无数据，db.js 会空表启动（应用照跑，但旧 demo 选手/评委可能丢失，需重加）。
